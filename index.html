AI Roadmap

Built around where I actually am: comfortable in SQL and Snowflake, Python basics down, new to building with AI. The main track turns my data background into AI skills that matter at work and in job interviews, with evals (checking whether AI answers are actually right) as my edge. Click a phase to expand it.

Foundation — fast, skip what I know AI Engineering — main track, work & career
0
Python, the data-person way Foundation

Not starting from zero. I already think in tables and queries, so the fastest route is learning Python by redoing things I already know how to do in SQL. Goal: comfortable enough that Python stops being the bottleneck. Target: about 3–4 weeks.

Take 3 queries I've written at work (joins, group-bys, window functions) and rebuild them in pandas on fake data
Set up a proper project: virtual environment, pip installs, a .env file for keys that never gets committed to GitHub
Call a free public API from Python, parse the JSON, and load it into a table
Query Snowflake from Python with the Snowflake connector (on a free trial account, not work data)
Git for real: branches, commits with real messages, every project from here on lives on GitHub
// pandas "Comparison with SQL" — made for exactly this · Automate the Boring Stuff for filling gaps
1
How LLMs work (2 weekends, max) Foundation

Enough to understand what's happening under the hood without going down the math rabbit hole. Hard time limit, because this is the part that's easy to keep "studying" forever instead of building. Can run alongside Phase 0.

Tokens, context windows, and why long inputs cost more and get less reliable
Embeddings: text turned into numbers so meaning can be compared (this comes back in Phase 4)
Training vs. inference, and why models hallucinate (they predict likely text, not true text)
Explain all of the above out loud to someone in 5 minutes without notes
// 3Blue1Brown's neural network series · Karpathy's "Intro to Large Language Models"
2
First real tool: SQL explainer AI Engineering

Learn the API by building something I'd actually use: a tool that reads a SQL script and writes plain-English documentation for it. That's half of what documenting a legacy pipeline is, so this lines up directly with work.

Before touching any work code: check what my company allows to be sent to outside AI services (insurance = strict). Use my own sample SQL until that's clear
Call the Claude or OpenAI API from Python and get a response back
Use a system prompt and get structured JSON back: purpose, source tables, output tables, business logic, open questions
Add tool use: let the model look up a table's columns instead of guessing them
Build: a command-line tool that takes a folder of .sql files and outputs a markdown doc for each
// Anthropic API docs · DeepLearning.AI short courses
3
Evals: my edge AI Engineering

Evals means testing whether an AI system's answers are actually right, at scale, instead of eyeballing a few. It's basically data reconciliation pointed at AI output, which is literally my day job. Most people building with AI skip this, and it's what companies deploying AI struggle with most.

Build a "golden set": 20–30 SQL scripts where I've written the correct answer myself (which tables it reads, what it outputs)
Write a script that runs the Phase 2 tool on the golden set and scores it: exact-match checks for the hard facts, a second model grading the fuzzy parts
Store every run's results in a table and compare: does a prompt change or a different model actually improve the score?
Read through the failures by hand and group them by type. Write up what I learned on this site
// Hamel Husain's writing on evals — the most practical stuff out there · Anthropic docs on testing & evaluation
4
RAG over data I know AI Engineering

Retrieval-augmented generation (RAG): giving the model the right documents at question time instead of relying on what it memorized. The docs from Phase 2 become the data source, so these phases stack instead of being separate tutorials.

Understand vector search: searching by meaning instead of exact keywords
Load the Phase 2 docs into Chroma (a simple local vector database)
Build: ask "which scripts touch this table?" or "where does this column come from?" and get grounded answers with sources
Measure it with a Phase 3-style eval set instead of guessing whether it works
Look into Snowflake Cortex: the same idea, but running inside Snowflake, which is likely the version my company would actually approve
// Chroma quickstart · Snowflake Cortex docs
5
Agents, applied at work AI Engineering

An agent is a model that takes several steps on its own: plan, run a tool, check the result, repeat. This is where it lands at work, on the reconciliation and Snowflake problems I already deal with. One small thing a teammate actually uses beats ten demos.

Write a simple agent loop by hand (no framework) so I understand what frameworks are doing for me
Build: plain-English question → SQL → results, against a sandbox schema
Eval it the reconciliation way: compare the agent's result set to a hand-written correct query's result set
Build: a mismatch investigator. Give it two sources that disagree; it queries both and explains the likely cause
Get one teammate to use something I built, collect their feedback, and turn it into a resume bullet with a real number
// Anthropic's "Building effective agents" · Snowflake Cortex Analyst (text-to-SQL inside Snowflake)
6
Ship one public project AI Engineering

Work projects can't be shown publicly, so I need one thing anyone can see. One project, finished, beats five half-started ones. Pick it, scope it small, ship it.

Pick ONE personal project with AI inside it, ideally one built on data (like using my own Whoop or fitness data), and write down what "done" means before starting
Build it using everything above: API, structured output, retrieval or agents if it needs them
Include a small eval set in the repo showing how well it works (this alone sets it apart)
Public GitHub repo with a clear README, plus a write-up here on the site
